1. WORKSPACE SEGREGATION STRATEGY
   - All customer cloud data platforms must leverage a 3-tier isolated workspace environment framework: [Project]-DEV, [Project]-STAGE, and [Project]-PROD to separate development execution sandboxes from stable production resources.

2. GLOBAL NAMING CONVENTIONS
   - Workspace Level: fabric-ws-[customer_initials]-[project_name]-[env]
   - Data Pipeline Level: pipe_ingest_[source_system]_[entity_name]
   - Notebook Level: nb_transform_[medallion_zone]_[target_table]
   - Lakehouse Catalog Tables: [zone]_[schema]_[table_name]

3. MULTI-ENVIRONMENT PATTERN STRATEGY
   - Multi-environment synchronization must be driven purely via automated Git branch bindings: Development workspace binds to the 'dev' branch, and Production workspace binds to the 'main' branch.

4. CONTROLLED ACCESS MODEL
   - Data Engineers / Developers: Assigned 'Contributor' role inside DEV/STAGE workspaces; restricted to 'Viewer' permissions in PROD.
   - Core Automation Services: Authenticated via dedicated Service Principals or explicit Workspace Identity tokens.
   - Business Analysts / End Users: Granted 'Viewer' access strictly targeting Gold tables or dedicated Power BI workspace reader permissions.

5. GIT INTEGRATION MANAGEMENT
   - Source code version tracking must use GitHub Enterprise repositories. Direct changes to the 'main' branch are blocked. All adjustments require a formal Pull Request (PR) with mandatory 2-person engineering review sign-offs.

6. OPERATIONAL MONITORING EXPECTATIONS
   - Pipeline statuses, processing times, and compute capacity usage metrics must be monitored daily through the Fabric Monitor Hub. Critical execution failures must automatically fire immediate alerts via automated Slack or Microsoft Teams webhooks.
